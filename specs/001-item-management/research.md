# 調査結果: Endfield 武器＆スキル早見アプリ

**フェーズ0 出力** | **日付**: 2026-04-15
**解決対象**: 技術コンテキストの NEEDS CLARIFICATION 項目

---

## 1. フロントエンドフレームワーク選定

### 決定事項

React 19 + Vite 8（CSR SPA）

### 根拠

- 2画面構成（`/weapons` / `/weapons/:weaponId`）のシンプルな SPA に最適
- Vite は TypeScript strict mode のサポートが標準かつビルドが高速
- React Router v7 で URL ルーティングを簡潔に実現
- `useState` / `useEffect` で IndexedDB 連携が素直に実現できる
- Vitest が Vite プロジェクトにネイティブ統合可能（設定ファイル兼用）

### 検討した代替案を却下した理由

| 案            | 却下理由                                                                                                          |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| **SvelteKit** | SSR を持つが本アプリは完全 CSR のため不要なオーバーヘッド                                                         |
| **Astro**     | 動的インタラクション（IndexedDB・フィルター・画像アップロード）が多く、Astro のハイドレーション設計と噛み合わない |
| **Next.js**   | SSR / SSG が不要。フロントエンドのみで完結するため過剰                                                            |

## 2. IndexedDB アクセス手段

### 決定事項

`idb` ライブラリ v8.x（Jakob Müller 著の薄い Promise ラッパー）

### 根拠

- ネイティブ IndexedDB API はコールバックベースで非同期操作が複雑になりコンスティテューション II（早期リターン）違反を誘発しやすい
- `idb` は Promise ベースの薄いラッパーで TypeScript 型安全性が高い
- バンドルサイズが小さい（約 1.5 KB gzip）
- `openDB` / `get` / `put` / `delete` の4関数で今回の全用途が完結

### 検討した代替案を却下した理由

| 案                            | 却下理由                                                        |
| ----------------------------- | --------------------------------------------------------------- |
| **Dexie.js**                  | 高機能だが本用途より大きく過剰                                  |
| **ネイティブ IDB API 直実装** | テスト容易性が低く、コンスティテューション III 違反リスクが高い |

## 3. CSS 戦略

### 決定事項

CSS Modules（`*.module.css`）

### 根拠

- Vite がネイティブサポートしており追加設定不要
- コンポーネントスコープのスタイルで命名衝突を防止
- 外部依存を最小化し、仕様の実装に集中できる

### 検討した代替案を却下した理由

| 案                    | 却下理由                                                        |
| --------------------- | --------------------------------------------------------------- |
| **Tailwind CSS**      | クラス名の学習コストがあり、小規模アプリでは CSS Modules で充分 |
| **styled-components** | ランタイムコストが発生する                                      |

## 4. weapons.json バリデーション戦略

### 決定事項

`JSON.parse` 後に型ガード関数（`isValidWeapon`）で各エントリを検証する純粋関数アプローチ

### 根拠

- 仕様「データ読み込みエラーの区別」に従い、不正エントリのみ除外する graceful degradation が必要
- 純粋関数として実装すれば Vitest でブラウザ環境なしにテスト可能（コンスティテューション III 準拠）
- JSON 全体が壊れた場合は `JSON.parse` の throw を catch して全体エラー扱い

### 検討した代替案を却下した理由

| 案                | 却下理由                                                                     |
| ----------------- | ---------------------------------------------------------------------------- |
| **Zod / Valibot** | 機能は優れるが、今回の単純な型ガードには過剰でありバンドルサイズを増加させる |

## 5. テスト戦略

### 決定事項

Vitest 4.x + React Testing Library（RTL）+ jsdom + `fake-indexeddb`

### 根拠

- Vitest は Vite ネイティブで設定が最小化できる
- `fake-indexeddb`: IndexedDB アダプターをインメモリでテストでき、モック化が容易（コンスティテューション III 準拠）
- RTL はユーザー操作起点のテストを促進し、実装詳細へのカップリングを抑える

### テスト対象の優先順位

| 優先度 | 対象                                              | 種別                       |
| ------ | ------------------------------------------------- | -------------------------- |
| P1     | `weaponLoader.ts`（JSON 読み込み+バリデーション） | ユニット                   |
| P1     | `imageValidator.ts`（サイズ・形式チェック）       | ユニット                   |
| P1     | `IndexedDbImageStorage.ts`（保存・取得・削除）    | ユニット（fake-indexeddb） |
| P2     | `WeaponDetailPage`（スキル表示・画像操作フロー）  | インテグレーション         |
| P3     | `WeaponsPage`（検索・フィルター）                 | インテグレーション         |
